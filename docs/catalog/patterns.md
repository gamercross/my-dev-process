# 패턴 카탈로그

7단계(유지보수)에서 새로 배운 패턴이 쌓이는 곳. 3단계(패턴 분석)에서 검색/참조합니다.
항목은 Volere 카드 형식으로 통일합니다.

## 항목 형식

```
## <패턴 이름>

- 트랙: 알고리즘 / 프로젝트
- 계층: 설계 패러다임 / 구현 기법 패턴 (알고리즘) — 또는 아키텍처 스타일 (프로젝트)
  ([03-pattern-analysis](../03-pattern-analysis/01-algorithm-paradigms.md) 분류 참고)
- 태그:
- 언제 쓰는가:
- 트레이드오프:
- 예시 문제/사례:
- 처음 배운 날짜/출처:
```

> `트랙`/`계층` 필드는 2026-09-17 회고에서 추가됨 — 항목이 쌓이면 알고리즘 기법과
> 아키텍처 패턴이 검색에서 뒤섞이는 걸 막기 위함 (전체 시스템 점검에서 발견).

## 해시맵 원패스 탐색 (Hash Map One-Pass Lookup)

- 트랙: 알고리즘
- 계층: 구현 기법 패턴 (CLRS 4대 설계 패러다임에는 안 속함)
- 태그: 해시맵, 원패스, 탐색
- 언제 쓰는가: 배열을 한 번 순회하며 "지금까지 본 것"을 해시맵/해시셋에 저장해두고,
  각 원소마다 "필요한 조건이 이미 봤던 것 중에 있는가"를 O(1)에 확인할 수 있을 때.
  저장하는 게 꼭 "봤는지 여부"(boolean)일 필요는 없다 — **마지막으로 본 인덱스**나
  **마지막으로 본 값** 등, 나중에 O(1)로 조회하고 싶은 걸 저장하면 된다. 이중 루프
  브루트포스(O(n²))를 O(n)으로 줄이는 가장 흔한 방법.
- 트레이드오프: 시간 O(n) 대신 공간 O(n) 추가 사용. 정렬이 필요 없어 투 포인터보다
  구현이 간단하지만, 입력이 이미 정렬돼 있고 메모리가 빠듯하면 투 포인터가 더 나을 수 있음.
- 예시 문제/사례:
  - [Two Sum](../01-problem-save/sessions/algorithm-track/2026-09-17-two-sum.md) —
    브루트포스(이중 루프)로 먼저 정답 확인 후, 해시맵으로 최적화하는 게 자연스러운 다음 단계.
    "값 → 인덱스" 저장.
  - [Contains Duplicate](../01-problem-save/sessions/algorithm-track/2026-09-17-contains-duplicate.md) —
    "해시" 키워드로 이 카탈로그에서 검색해 재사용 확인 (핵심 피드백 루프 실증, 2026-09-17).
    "값을 봤는지"(해시셋)만 저장.
  - [Contains Duplicate II](../01-problem-save/sessions/algorithm-track/2026-09-19-contains-duplicate-ii.md) —
    "값 → **마지막으로 본 인덱스**"를 저장하는 변형. boolean이 아닌 값을 저장해도
    패턴의 핵심 원리는 그대로 적용됨을 확인(2026-09-19).
- 처음 배운 날짜/출처: 2026-09-17, Two Sum 드라이런 회고. 2026-09-19,
  Contains Duplicate II에서 세 번째로 재사용되며 설명을 일반화.

## 환경변수 기반 Config 오버라이드

- 트랙: 프로젝트
- 계층: 구현 기법 (Twelve-Factor App의 Config 원칙을 코드 수준에서 구현하는 방법 —
  5대 아키텍처 스타일 어디에도 속하지 않는 횡단 관심사라 "구현 기법"으로 분류)
- 태그: 설정, 환경변수, Twelve-Factor, 이식성
- 언제 쓰는가: 로컬 도구가 읽는 데이터/설정의 위치를 하드코딩하면, 다른 저장소나
  다른 환경에서 재사용할 때마다 코드를 고쳐야 한다. 기본값은 코드 안에 두되,
  환경변수가 있으면 그걸 우선한다.
- 트레이드오프: 설정 주입 경로가 하나 늘어나는 대신(환경변수 미설정 시 실수로
  기본값을 쓰는 걸 눈치 못 챌 수 있음), 코드 수정 없이 다른 환경에 바로 적용
  가능해진다.
- 예시 문제/사례:
  - [카탈로그 검색 CLI](../01-problem-save/sessions/project-track/2026-09-19-catalog-search-cli.md) —
    `CATALOG_ROOT` 환경변수로 검색 대상 저장소를 바꿀 수 있게 함(FR4)
- 처음 배운 날짜/출처: 2026-09-19, 카탈로그 검색 CLI 회고 (이 저장소의 첫
  프로젝트 트랙 패턴 등록)

## 스택 기반 매칭 (Stack-Based Matching)

- 트랙: 알고리즘
- 계층: 구현 기법 패턴 (CLRS 4대 설계 패러다임에는 안 속함)
- 태그: 스택, 괄호매칭, 짝맞춤
- 언제 쓰는가: "여는 것"과 "닫는 것"이 짝을 이뤄야 하고, 가장 최근에 열린 것부터
  닫혀야 하는(LIFO) 문제. 여는 원소를 스택에 쌓아두고, 닫는 원소가 나올 때마다
  스택 맨 위와 짝이 맞는지 O(1)에 확인한다.
- 트레이드오프: 문자열/시퀀스를 반복 치환하는 브루트포스(O(n²))보다 한 번의
  순회로 끝나 O(n). 길이가 홀수면 애초에 무효라는 것처럼, 입력의 명백한 무효
  조건을 스택을 만들기 전에 먼저 걸러내면(빠른 실패) 상수 배 정도 더 빨라진다.
- 예시 문제/사례:
  - [Valid Parentheses](../01-problem-save/sessions/algorithm-track/2026-09-19-valid-parentheses.md) —
    브루트포스(반복 치환)로 먼저 정답 확인 후, 스택으로 최적화
- 처음 배운 날짜/출처: 2026-09-19, Valid Parentheses 회고 (카탈로그의 두 번째
  구현 기법 패턴 — 첫 번째 "해시맵 원패스 탐색"과는 다른 유형의 문제도 담을 수
  있다는 걸 확인)

## 한 번 순회 최솟값 추적 (Single-Pass Min Tracking — Greedy)

- 트랙: 알고리즘
- 계층: 설계 패러다임 (CLRS 4대 패러다임 중 **그리디**)
- 태그: 그리디, 한번순회, 최솟값
- 언제 쓰는가: "지금까지 본 것 중 최선(최솟값/최댓값)"과 "지금 원소로 얻을 수
  있는 결과"만 비교하면 되고, 나중에 나올 원소가 그 판단을 뒤집을 수 없는 문제.
  매 단계에서 지역적으로 최선인 선택(여기서는 "지금까지의 최솟값 갱신")을 하고
  절대 번복하지 않는다는 점에서 그리디. 모든 (i, j) 쌍을 보는 이중 루프
  브루트포스(O(n²))를 O(n)으로 줄인다.
- 트레이드오프: 추가 메모리 없이(O(1) 공간) O(n)에 끝나 "해시맵 원패스 탐색"보다도
  가볍다. 다만 "미래 선택이 과거 선택을 뒤집을 수 없다"는 전제가 깨지면(예: 매수·
  매도를 여러 번 할 수 있는 변형) 그리디만으로는 부족해지고 DP가 필요해진다.
- 예시 문제/사례:
  - [Best Time to Buy and Sell Stock](../01-problem-save/sessions/algorithm-track/2026-09-22-best-time-to-buy-and-sell-stock.md) —
    "지금까지 본 최저가"만 추적하며 그 시점 가격과의 차이로 최대 이익 갱신
- 처음 배운 날짜/출처: 2026-09-22, Best Time to Buy and Sell Stock 회고
  (카탈로그의 세 번째 구현 패턴이자 첫 CLRS 설계 패러다임 항목 — 지금까지는
  모두 "구현 기법 패턴"이었음)
