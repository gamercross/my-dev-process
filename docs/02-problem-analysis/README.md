# 2단계: 문제 분석

문제 저장 단계에서 받은 원문제를 실제로 다룰 수 있는 요구사항으로 쪼개는 단계.

## 사용하는 4가지 도구

1. **ISO/IEC/IEEE 29148** — 기능 요구사항을 5요소로 쪼갬: `[조건] [주체] [행동] [대상] [제약]`
2. **FURPS+** — 비기능 요구사항을 5범주로 분류 (Functionality/Usability/Reliability/
   Performance/Supportability)
3. **Volere Atomic Requirement Shell** — 요구사항 하나하나를 카드로 기록: ID, 설명, 유형,
   근거(Rationale), 출처(Originator), 충족기준(Fit Criterion)
4. **MoSCoW** — Must/Should/Could/Won't 우선순위 분류

## 적용 예시: 이 워크플로우 시스템 자체의 요구사항

아래는 이 저장소(나만의 개발 워크플로우 시스템)를 만들 때 실제로 도출한 요구사항입니다.
템플릿을 어떻게 채우는지 참고용으로 남겨둡니다.

### 기능 요구사항

| ID | 요구사항 | 근거 | 충족기준 | 우선순위 |
|---|---|---|---|---|
| FR1 | 사용자가 새 문제/프로젝트를 시작하면, 시스템은 트랙에 맞는 저장 템플릿을 제공해야 한다 | 즉흥적 시작 방지 | 필수 필드 미기입 시 다음 단계 진행 불가 | Must |
| FR2 | 사용자가 패턴을 검색하면, 시스템은 태그/키워드로 일치하는 카탈로그 항목을 반환해야 한다 | 과거 패턴 재사용 안 됨 | 로컬 파일 기준 즉시 결과 표시 | Should |
| FR3 | 유지보수 단계 완료 시, 시스템은 회고 내용을 카탈로그/체크리스트에 추가하는 진입점을 제공해야 한다 | 원문제 핵심(피드백 루프) | 회고 후 1회 명령으로 카탈로그 항목 추가 가능 | Must |

### 비기능 요구사항

| 범주 | 요구사항 | 측정 기준 |
|---|---|---|
| Usability | 각 단계 템플릿은 5분 이내 작성 가능 | 필드 수 ≤ 7개/단계 |
| Supportability | 새 트랙 추가 시 기존 구조 무변경으로 확장 가능 | 기존 파일 수정 없이 신규 템플릿 파일만 추가 |
| Reliability | 저장 데이터 유실 방지 | 파일 기반 + git 버전관리 |

### 우선순위 요약 (MoSCoW)
- **Must**: FR1, FR3
- **Should**: FR2
- **Could**: 자동 알림/자동 반영
- **Won't (지금은)**: GUI, 웹앱화
