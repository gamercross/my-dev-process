제목: Best Time to Buy and Sell Stock
출처(플랫폼, 문제번호): LeetCode #121
시나리오(원문 요약): 주식의 날짜별 가격이 담긴 배열이 주어질 때, 하루에 한 번 매수하고
그 이후 하루에 한 번 매도해서 얻을 수 있는 최대 이익을 구한다. 이익을 낼 수 없으면 0을
반환한다.
입력 형식 + 제약조건(수학적 표기, 예: 1 ≤ n ≤ 10^5): prices(정수 배열, 1 ≤ len(prices) ≤ 10^5, 0 ≤ prices[i] ≤ 10^4)
출력 형식: 최대 이익(정수, 0 이상)
예제 입출력(최소 1쌍): prices=[7,1,5,3,6,4] → 5 (1일차 1에 매수, 4일차 6에 매도) / prices=[7,6,4,3,1] → 0
태그(3단계 패턴 분류와 연결): 그리디, 한 번 순회 최솟값 추적
상태(미착수 / 분석중 / 풀이완료 / 복습필요): 풀이완료

## 3단계: 패턴 분석

`catalog/patterns.md`를 "그리디", "최소값", "주식" 키워드로 검색 → **일치하는
항목 없음**. 이 시스템이 개선된 뒤 처음으로 실제 문제에서 SKILL.md의 새
지시("규모 판단 전에 patterns.md를 먼저 훑어본다")를 그대로 따른 사례이기도
하다 — 검색은 실패했지만 실패했다는 사실 자체가 규모 판단(Xpress)의 근거
중 하나였다: 기존 등록 패턴은 없어도, 표준 카탈로그(그리디 패러다임)로
바로 풀리는 문제라 Xpress가 맞다.

표준 카탈로그로 폴백: `03-pattern-analysis/01-algorithm-paradigms.md`의
그리디(Greedy) 패러다임 — "각 단계에서 지역적으로 최선인 선택을 하고, 그
선택을 번복하지 않는다"는 정의가 그대로 들어맞는다. 배열을 한 번 순회하며
"지금까지 본 최솟값"만 갱신하고, 그 시점 가격과의 차이가 지금까지의 최대
이익보다 크면 갱신 — 미래를 다시 보지 않으므로 그리디.

**게이트**: `3 → 4` = Go — 표준 카탈로그(그리디)로 분류, 선택 근거 기록 완료.

## 4단계: 패턴 구현 (스켈레톤)

"Make it work" 원칙대로 브루트포스부터: 모든 (매수일, 매도일) 쌍 중
`prices[j] - prices[i]`(매도일이 매수일보다 뒤)의 최댓값을 구한다.
[`implementations/algorithm-track/best-time-to-buy-and-sell-stock/solution.py`](../../../../implementations/algorithm-track/best-time-to-buy-and-sell-stock/solution.py)에

```
$ python3 -c "from solution import max_profit_bruteforce as f; \
  print(f([7,1,5,3,6,4]), f([7,6,4,3,1]))"
5 0
```

**게이트**: `4 → 5` = Go — 브루트포스가 정답을 냄.

## 5단계: 구현

동등분할/경계값 분석으로 테스트 7개 설계:
- 배열 길이 하한(1) — 매수/매도 쌍 자체 불가능, 항상 0
- 단조 감소 — 항상 손해, 항상 0인 클래스
- 단조 증가 — 이익이 (마지막-첫값)과 같아야 하는 클래스
- 모든 값이 같음 — 경계: 이익 0
- **최댓값이 최솟값보다 앞서 나오는 경우** — "매도가 매수보다 반드시 뒤"라는
  제약을 실제로 어기는 쌍을 답으로 쓰면 안 됨(브루트포스도 같이 검증)
- 브루트포스 대비 차등 테스트(무작위 200회)

이번에도 4단계 브루트포스가 이미 정답을 맞혀서 Red 구간 없음(7개 테스트가
브루트포스로 바로 통과). Refactor에서 O(n) 한 번 순회(최솟값 추적) 방식으로
교체, 재통과.

`run_all_tests.py`로 6개 구현(38개 테스트) 전체 통과 확인.

**게이트**: `5 → 6` = Go — 단위 테스트 통과, 경계값 분석으로 엣지 케이스 커버.

## 6단계: 서비스

브루트포스는 가지치기가 없어 항상 O(n²) — 무작위(중복 없는) 가격 배열이
진짜 최악 케이스다. 지난 회고들의 체크리스트(벤치마크 추세 먼저 확인)를
그대로 적용:

| n | 브루트포스 | 직전 대비 |
|---|---|---|
| 500 | 3.8 ms | — |
| 1,000 | 14.8 ms | 3.9배 |
| 2,000 | 56.2 ms | 3.8배 |
| 4,000 | 226.3 ms | 4.0배 |

약 4배씩 증가 확인(진짜 O(n²)). 제약조건 상한(n=100,000)에서 최적화 버전만
측정: **5.846 ms** — 브루트포스는 이 크기에서 추세로 추정하면 2분 이상 걸려
비현실적.

**게이트**: `6 → 7` = Go — 성능 실측 완료(추세로 검증됨).

## 7단계: 유지보수 (회고)

문제/프로젝트: Best Time to Buy and Sell Stock (Xpress 등급, 다섯 번째 알고리즘 항목)

잘된 점: 이번 항목은 원래 목적이 "지난 세션에 고친 SKILL.md 절차가 실전에서
실제로 동작하는지" 검증하는 것이었다 — 결과적으로 SKILL.md 명령 1의 새 지시

마찰 없이 작동했다. 또한 세션을 시작하자마자 로컬 저장소(`.git`)가 손상되어
있는 걸 발견했는데(`HEAD`/`config` 유실, 템플릿 파일까지 사라짐), GitHub에
푸시된 최신 커밋으로 다시 클론해서 즉시 복구했다 — 이 시스템의 진짜 산출물이
로컬 파일이 아니라 원격 저장소에 있다는 걸 실제로 확인한 사례.

어려웠던 점: 없음 — 다만 "로컬 작업 디렉터리가 예고 없이 손상될 수 있다"는
게 이번에 처음 실제로 발생했다.
  → 5 Whys:
    1. 왜 로컬 디렉터리가 손상됐나? → `.git`의 `HEAD`/`config`와 일부 문서
       파일이 사라져 있었다.
    2. 왜 사라졌나? → 이 세션을 실행하는 스크래치 워크스페이스 자체가
       세션 사이에 재구성/재동기화되는 환경이고, 그 과정이 완전하지
       않았던 것으로 보인다 (이 저장소 코드의 버그가 아니라 실행 환경의
       특성).
    3. 왜 이게 이 워크플로우 시스템의 문제가 되는가? → 지금까지 "작업은
       항상 로컬에 안전하게 있다"고 암묵적으로 가정하고 있었다 — 복구
       절차가 문서화돼 있지 않았다.
    4. 왜 아직 문서화가 안 됐나? → 지금까지는 로컬 환경이 항상 온전했기
       때문에 필요성을 못 느꼈다.
    → 근본원인: 이 시스템은 "로컬 작업 디렉터리가 깨질 수 있다"는 전제를
      세워둔 적이 없었다. Blameless하게 보면 사람의 실수가 아니라
      **복구 절차의 부재**가 원인.

새로 배운 패턴: "한 번 순회 최솟값 추적"(그리디) — `catalog/patterns.md`에
새 항목으로 등록 (아래 참고).

놓쳤던 체크리스트 항목: **"세션 시작 시 `git status`가 실패하면(저장소가
