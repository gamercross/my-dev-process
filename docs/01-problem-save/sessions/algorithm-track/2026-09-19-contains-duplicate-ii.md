입력 형식 + 제약조건(수학적 표기, 예: 1 ≤ n ≤ 10^5): nums(정수 배열, 1 ≤ len(nums) ≤ 10^5, -10^9 ≤ nums[i] ≤ 10^9), k(정수, 0 ≤ k ≤ 10^5)
출력 형식: boolean (true/false)
예제 입출력(최소 1쌍): nums=[1,2,3,1], k=3 → true / nums=[1,2,3,1,2,3], k=2 → false

## 3단계: 패턴 분석

`catalog/patterns.md`를 "해시맵" 키워드로 검색 → **기존 "해시맵 원패스 탐색"
패턴이 실제로 검색됨** (네 번째 항목이자, 이 패턴의 세 번째 재사용 — Two Sum,
Contains Duplicate에 이어). 이번엔 완전히 같은 형태가 아니라 "거리 제한(k)"이
붙은 변형이라, 패턴이 정말 일반적인지 검증하는 사례이기도 하다.

선택 근거: 값을 볼 때마다 "마지막으로 본 인덱스"를 해시맵에 저장해두고, 같은
값을 다시 만나면 이번 인덱스와의 거리를 O(1)로 바로 비교할 수 있다 — 기존
패턴의 "지금까지 본 값을 저장해두고 조회"라는 핵심 아이디어를 그대로 쓰되,
저장하는 값이 "봤는지 여부"가 아니라 "마지막 인덱스"로 바뀐 것뿐이다.

**게이트**: `3 → 4` = Go — 기존 패턴 재사용, 선택 근거 기록 완료.

## 5단계: 구현

동등분할/경계값 분석으로 테스트 7개 설계:
- `k=0` — 동등분할: i≠j가 필요하므로 항상 False인 클래스
- 배열 길이 하한(1) — 쌍 자체 불가능
- 거리가 **정확히 k**(포함) vs **k+1**(제외) — 경계값
- `k`가 배열 길이 이상 — 일반 Contains Duplicate와 동치인 클래스
- 음수, 브루트포스 대비 차등 테스트(무작위 200회)

Valid Parentheses 때처럼 4단계 브루트포스가 이미 정답을 맞혀서 Red 구간
없음(7개 테스트가 브루트포스로 바로 통과). Refactor에서 해시맵 최적화로
교체 — "봤는지 여부" 대신 "마지막으로 본 인덱스"를 저장하는 변형. 교체 후
7개 재통과.

`run_all_tests.py`로 5개 구현(31개 테스트) 전체 통과 확인.

**게이트**: `5 → 6` = Go — 단위 테스트 통과, 경계값 분석으로 엣지 케이스 커버.

## 6단계: 서비스

브루트포스는 `j-i>k`인 쌍도 그대로 확인하는(가지치기 없음) 구조라 k 값과
무관하게 항상 O(n²) — 중복 없는 배열이 진짜 최악 케이스다. Contains
Duplicate 회고의 교훈대로 상한에서 바로 재지 않고 추세부터 확인:

| n | 브루트포스 | 직전 대비 |
|---|---|---|
| 500 | 2.5 ms | — |
| 1,000 | 10.0 ms | 4.0배 |
| 2,000 | 42.2 ms | 4.2배 |
| 4,000 | 163.2 ms | 3.9배 |

약 4배씩 증가 확인(진짜 O(n²)). 제약조건 상한(n=100,000)에서 해시맵 버전만
측정: **10.57 ms** — 브루트포스는 이 크기에서 직접 측정하면 추세로 추정 시
1~2분 걸려 비현실적.

**게이트**: `6 → 7` = Go — 성능 실측 완료(추세로 검증됨).
