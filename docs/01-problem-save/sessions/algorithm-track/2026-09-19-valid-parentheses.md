제목: Valid Parentheses
출처(플랫폼, 문제번호): LeetCode #20
시나리오(원문 요약): 괄호 문자로만 이루어진 문자열이 주어질 때, 여는 괄호와 닫는 괄호가 올바른 순서와 짝으로 맞춰져 있는지 판별한다.
입력 형식 + 제약조건(수학적 표기, 예: 1 ≤ n ≤ 10^5): s(문자열, 1 ≤ len(s) ≤ 10^4, '(', ')', '{', '}', '[', ']'로만 구성)
출력 형식: boolean (true/false)
예제 입출력(최소 1쌍): s="()[]{}" → true, s="(]" → false
태그(3단계 패턴 분류와 연결): 스택, 괄호매칭
상태(미착수 / 분석중 / 풀이완료 / 복습필요): 풀이완료

## 3단계: 패턴 분석

`catalog/patterns.md`를 "스택"·"괄호" 키워드로 검색 → **일치 항목 없음**(지금까지
등록된 패턴은 "해시맵 원패스 탐색" 하나뿐). SKILL.md 명령 2 step 3대로 표준
카탈로그([01-algorithm-paradigms.md](../../../03-pattern-analysis/01-algorithm-paradigms.md))로
폴백 — 이 저장소에서 "검색 실패 → 폴백" 경로가 실제로 처음 타본 사례.

CLRS 4대 설계 패러다임(분할정복/DP/그리디/백트래킹) 중 어디에도 깔끔히 안 맞음 —
Two Sum의 해시맵처럼 이것도 **구현 기법 패턴**(스택 기반 매칭)에 해당한다.
선택 근거: 여는 괄호를 스택에 쌓아두고 닫는 괄호가 나올 때마다 스택 맨 위와
짝이 맞는지 확인하면 한 번의 순회로 판별 가능 — 그 외 대안(정규식으로 반복
치환 등)보다 직관적이고 O(n)이 자연스럽게 나옴.

**게이트**: `3 → 4` = Go — 선택 근거 기록 완료.

## 4단계: 패턴 구현 (스켈레톤)

"Make it work" 원칙대로 브루트포스부터: 짝이 맞는 괄호 쌍("()", "[]", "{}")을
문자열에서 찾을 때마다 제거하는 걸 더 이상 지울 게 없을 때까지 반복하고, 마지막에
빈 문자열이면 true. [`implementations/algorithm-track/valid-parentheses/solution.py`](../../../../implementations/algorithm-track/valid-parentheses/solution.py)에
`valid_parentheses_bruteforce`로 구현, 예제 케이스로 스모크 테스트:

```
$ python3 -c "from solution import valid_parentheses_bruteforce as f; \
  print(f('()[]{}'), f('(]'), f('([)]'), f('{[]}'))"
True False False True
```

**게이트**: `4 → 5` = Go — 위 스모크 테스트로 브루트포스 정답 확인.

## 5단계: 구현

[`test_solution.py`](../../../../implementations/algorithm-track/valid-parentheses/test_solution.py)를
동등분할/경계값 분석으로 설계:

- 길이 하한(1) — 홀수라 항상 무효
- 홀수 길이 클래스 전체(패리티만으로 무효 판정 가능)
- **짝수 길이인데 구조가 잘못된 경우** (`([)]`, `))((`) — 패리티로는 못 거르는,
  진짜 스택 로직이 필요한 케이스
- 중첩 유효 케이스, 길이 상한(10^4)
- 브루트포스 대비 차등 테스트(무작위 200회)

Two Sum 때와 달리 **Red 구간이 없었다** — 4단계 브루트포스가 이미 7개 테스트를
전부 통과했다(브루트포스도 정답 자체는 맞으니 당연함). Refactor(최적화) 단계에서
스택 기반 O(n)으로 교체 — "길이가 홀수면 무조건 무효"라는 빠른 실패 조건도 추가
(동등분할에서 나온 클래스 구분을 그대로 코드에 반영). 교체 후 7개 테스트 재통과.

`python3 implementations/run_all_tests.py`로 4개 구현(24개 테스트) 전체가 함께
통과하는 것도 확인.

**게이트**: `5 → 6` = (대기) — 6단계(성능 실측)는 다음 진행.

## 6단계: 서비스

지난 회고([catalog/checklist.md](../../../catalog/checklist.md) "6단계 성능
실측 체크리스트")에서 배운 대로, "최악 케이스"라고 주장하기 전에 여러 크기에서
실제로 돌려서 추세부터 확인했다. 완전히 중첩된 문자열("((...))")은 매 순회마다
가운데 "()" 하나만 지워지고 매번 전체를 다시 훑으므로 진짜 O(n²) 최악 케이스다.

[`benchmark.py`](../../../../implementations/algorithm-track/valid-parentheses/benchmark.py) 실측:

| len(s) | 브루트포스 | 배수(직전 대비) |
|---|---|---|
| 1,000 | 2.0 ms | — |
| 2,000 | 7.6 ms | 3.7배 |
| 4,000 | 30.0 ms | 4.0배 |
| 8,000 | 116.6 ms | 3.9배 |

크기를 2배씩 늘릴 때마다 시간이 약 4배씩 늘어나 O(n²) 추세가 실제로 확인됨
(Two Sum 때와 달리 이번엔 처음부터 진짜 최악 케이스였다).

제약조건 상한(n=10,000, 완전 중첩)에서: 브루트포스 179.2ms → 스택 0.383ms
(약 468배). 알고리즘 트랙 DoD(제출/채점+성능)의 "채점"은 5단계 테스트로,
"제출"은 세션 한계로 생략.

**게이트**: `6 → 7` = Go — 성능 실측 완료(추세로 검증된 진짜 최악 케이스).
