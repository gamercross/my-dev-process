# 발표 준비 시스템 (검증용 도구: 답변 카드 A)

트랙: [project-track](../../project-track.md) · 태그: presentation, qa-prep, decision-record, verification-tool

## 1단계 — 문제 저장

```
요약(Description):
  발표 준비 시스템. 사람이 자기 프로젝트를 이해하고, 나올 질문을 미리 알고,
  Q&A 답변을 준비하는 순환을 만든다. 이번 조각(1번)은 이 순환의 한 부분
  (질문 하나 → 답변 카드)을 검증하는 도구다. 시스템이 목적이고 도구는 검증용이다.

재현 절차 또는 배경(Motivation):
  면접·팀 공유·레퍼런스 시연에서 "왜 그렇게 결정했어요?"에 막힌다.
  기억은 나는데 말로 정리가 안 되고, 메모는 나중에 보면 이유가 기억나지 않아 실패한다.
  대상은 두 부류다.
    A. 워크플로우가 없어 결정 이유가 정리되지 않은 사람
    B. 워크플로우와 내용은 있지만 발표 방법을 모르는 사람
  최상위 목적: 사람들이 만든 프로젝트가 발표에서 좋은 성과를 내게 한다.
  (성과의 구체 정의는 미확정 — 2단계에서 정량화)

기대 동작 또는 제안 해결책(Expected behavior):
  사용자가 질문 하나를 주면 Claude가 인터뷰로 이유·대안·사례를 뽑아
  PREP 순서(결론, 이유, 사례, 결론)의 답변 카드를 만든다.
  목표(초안): 1분 이내, 결론 1문장 + 이유 최대 2개 + 사례 1개.
  정확한 값은 2단계에서 Planguage로 확정한다.

환경 정보:
  Claude Code 스킬 명령 (가정). 다른 곳으로 내보내기는 이번 범위 밖.

대안 검토(Alternatives considered):
  - 기존 방식: 메모 → 결정 당시 이유가 남지 않아 실패.
  - PREP은 "출처 확인 불가, 실무에서 통용되는 후보 구조"로 표시한다.
    (원 저자·공식 출처를 확인하지 못함. Toastmasters 공식 자료에도 PREP은 없었음)
  - 같은 조사에서 나온 다른 후보: Minto·SCQA, Duarte 스파크라인, Made to Stick(SUCCESs),
    Carnegie Magic Formula. 모두 공식 표준이 아니라 실무 프레임워크.
```

## 이번 조각에서 하지 않는 것

리허설, 1~2분·3분 이상 발표 흐름, 기존 기록(ADR·게이트 로그·회고) 자동 연결,
다른 곳으로 내보내기, 예상 질문 자동 생성(B 방식).

## 2단계에서 검증할 가정

1. 답변 카드를 준비하면 Q&A 준비 상태가 실제로 좋아진다. (성과와의 연결은 가설)
2. "1분 이내, 결론 1 + 이유 2 + 사례 1"이 적절한 기준이다.
3. PREP이 이 용도에 맞는 구조다.
4. A 부류와 B 부류에 같은 카드로 충분하다.

## 1단계 밖에서 나온 후속 입력 (3단계 이후에 다룸)

대화 중 요구사항과 설계가 섞여 나왔다. 1단계 DoD에는 속하지 않지만 잃지 않도록 남긴다.

- 조각 계획: ① 답변 카드(이 문서) → ② 리허설 → ③ 긴 발표 흐름 → ④ 기존 기록과 연결
  → ⑤ 내보내기(ADR-0002 필요, ADR-0001의 "개인 도구" 전제가 바뀜) + 예상 질문 생성(질문 기준 조사가 먼저).
- 시작 방식은 A(사용자가 질문을 가져옴). B(Claude가 예상 질문을 뽑음)는 A 검증 후.
- 답변 조립 구조 후보와 예상 질문 생성 기준은 별개다. 질문 기준(소크라테스식 질문 등)은 미조사.
- 기존 산출물의 발표 재료 대응(가설): 1단계 배경→SCQA, 2단계 Planguage→기준,
  3단계 ADR·ATAM→Reason, 게이트 로그→Example, 6단계 실측→증거, 7단계 5 Whys→통찰.
- PRD는 상세형으로 확장한다. (처음엔 "확장 안 함"으로 정했으나, 사용자마다 요구가 늘어날 것이므로
  피드백을 구체적으로 반영하기 위해 사용자가 결정을 바꿈. 아래 "1단계 확장 — PRD" 참고)

## 1단계 확장 — PRD (상세형, 초안)

결정: 2026-09-24 사용자가 확장으로 결정. 이유: 사용자마다 요구가 늘어날 것이므로 피드백을 구체적으로 반영하기 위해.
**이 PRD는 살아있는 문서다.** 검증(수작업 시연) 전의 내용은 확정이 아니라 초안이며, 항목마다 상태를 표시한다.
상태: **확정**(사용자가 확인) / **초안**(Claude가 대화에서 정리, 확인 필요) / **미정**(정보 없음).

```
Feature Overview [확정 2026-09-24]:
  발표 준비 시스템. 자기 프로젝트와 예상 질문을 미리 이해하고 Q&A 답변을 준비하는 순환.
  이번 조각(1번)은 "질문 하나 → 인터뷰 → PREP 답변 카드"로 가설을 검증하는 도구.

Business Justification [부분 확정]:
  확정: 가치는 두 층이다. (1) 개인 성장 (2) 팀의 발표 역량. 최상위 목적은 발표에서 좋은 성과.
  미정: 두 가치를 각각 어떻게 재는지("좋은 성과", "성장", "팀 역량"은 아직 정성적 표현).
        팀이 구체적으로 누구인지, 개인과 팀 가치가 부딪힐 때의 우선순위.

Technical Architecture [초안]:
  파일 + Claude Code 스킬 하이브리드(ADR-0001 승계). 다른 곳으로 내보내기와 다중 사용자 환경은
  ADR-0001의 "개인 도구" 전제가 깨지므로 ADR-0002가 필요하다(이번 범위 밖).

Security & Compliance [미정]:
  사용자의 프로젝트 결정과 받은 질문은 민감할 수 있다. 동의·익명화·보관 방식은 결정되지 않았다.
  여러 사람의 데이터를 모으기 전에 정해야 한다(수집 R20).

Testing Strategy [초안]:
  수작업 시연 후 전/후 비교(카드 없이 답한 것 vs 카드로 준비한 뒤 답한 것): 시간, 핵심 포함 여부.
  기준값은 2단계 3번 정량화에서 확정. 자동 테스트는 없음(ADR-0001 승계).

Participants(관련자) [미정]:
  사용자 A(워크플로우 없음), 사용자 B(워크플로우 있으나 발표 방법 모름), 요구 제공자(사용자 본인).
  시연 참여자와 최종 의사결정자는 아직 정해지지 않았다.

Status(현재 상태) [확정]:
  1단계 PRD 작성 중(게이트 Recycle). 2단계 수집 완료, EARS 명세 초안(FR1~8, 시연 후 확정).
  수작업 시연은 아직 안 했다. 실제 청중 질문 데이터는 0건.

Background & Strategic Fit [초안]:
  기존 dev-workflow가 쌓는 기록(ADR, 게이트 로그, 회고)을 발표 재료로 연결하려는 것.
  기록이 발표 재료가 된다는 대응은 가설이다.

User Stories [초안, 확인 필요]:
  US1 (A): 워크플로우 없는 사용자로서, 발표에서 받을 질문 하나에 대한 결정 이유를 정리하고 싶다.
           그래야 "왜 그렇게 결정했어요?"에 막히지 않는다.
  US2 (B): 워크플로우는 있는 사용자로서, 내 기록을 청중이 이해할 답변으로 바꾸고 싶다.
           그래야 발표 방법을 몰라도 Q&A에 대비할 수 있다.
  US3 (요구 제공자): 사용자로서 내 요구를 남기고 반영 여부를 알고 싶다.
           그래야 시스템이 내 상황에 맞게 바뀐다. (피드백 반영 방식은 미정)

UX 설계 [초안]:
  Claude Code 대화. 질문 입력 → 되묻기(한 번에 최대 2개) → 이유·대안·사례가 차면 PREP 카드
  → 소리 내어 시간 재기 안내. 말하지 못한 칸은 "미확인"으로 남긴다.

Scoping(범위) [초안]:
  포함: 질문 받기, 인터뷰, 답변 카드(FR1~8 중 시연에서 확인된 것).
  제외(후속 조각): 리허설, 긴 발표 흐름, 기존 기록 연결, 예상 질문 자동 생성, 내보내기, 데이터 가공.
  피드백 반영: 사용자 요구는 이 PRD의 User Stories와 Scoping에 반영하고, 변경 이유를 아래에 기록한다.
```

### 1. 수집 (BABOK)

사용한 기법: Interview(이 세션의 대화), Document Analysis(저장소 문서), Brainstorming(구조 후보).
**Observation은 못 썼다** — 실제 발표에서 받은 질문이나 막힌 순간의 기록이 아직 없어서다.
출처 표기: **[U]** 사용자 진술, **[C]** Claude의 제안·조사(가설 포함), **[D]** 저장소 문서.

**수집된 원자료**

| R2 | U | 막히는 상태는 "기억은 나는데 말로 정리가 안 됨" |

**수집의 한계 (명세로 넘어가기 전에 인지할 것)**
- 원자료 R1~R13이 **한 명의 진술**이다. A·B 부류의 필요(R4)는 그 사람의 관점이지 해당 사용자에게서 직접 확인한 것이 아니다.
- **실제 청중 질문 데이터가 없다.** 예상 질문의 기준을 세울 근거가 없어 R9는 이번 조각에서 다루지 않는다.
- R6(시간 기준)과 성과의 정의(최상위 목적)가 **아직 숫자가 아니다** — 3번 정량화에서 풀어야 한다.
- R13은 이해하지 못했으므로 요구사항으로 옮기지 않는다.

### 2. 기능 요구사항 (EARS) — 이번 조각(질문 받기 → 인터뷰 → 답변 카드)만

`shall` 뒤에는 행동 하나만 둔다. 시간·구성 기준의 숫자는 3번 정량화에서 확정하므로 `<기준>`으로 남긴다.
"근거"의 R번호는 위 수집 표를 가리킨다. **확인 필요** 표시는 원자료에 직접 없고 Claude가 추론해서 넣은 요구사항이다.

```
FR1 (Event-driven): When 사용자가 발표에서 받을 질문 하나를 입력하면,
                    the 시스템은 shall 그 질문에 답하는 데 필요한 이유·대안·사례를 사용자에게 되묻는다.
  근거: R1, R2
  충족기준: 질문 입력 직후 이유·대안·사례 중 비어 있는 항목에 대한 되묻기가 시작된다.

FR2 (Ubiquitous):   The 시스템은 shall 한 번에 최대 2개의 질문만 한다.
  근거: D (dev-workflow 인터뷰 규칙 "1~2개씩")
  충족기준: 어떤 턴에서도 물음표가 붙은 질문이 3개 이상 나오지 않는다.

FR3 (Event-driven): When 이유·대안·사례 세 항목이 모두 채워지면,
                    the 시스템은 shall PREP 순서(결론, 이유, 사례, 결론)의 답변 카드를 작성한다.
  근거: R2, R8
  충족기준: 카드가 결론 → 이유 → 사례 → 결론 순서로 나온다.

FR4 (Ubiquitous):   The 시스템은 shall 카드의 이유·대안·사례를 사용자가 말한 내용에서만 가져온다.
  근거: R3 (결정 이유가 기억나지 않는 문제는 남이 대신 지어내면 풀리지 않음) — **확인 필요**
  충족기준: 카드의 모든 이유·사례가 인터뷰 대화 속 사용자 발언과 대응된다.

FR5 (Unwanted):     If 사용자가 이유·대안·사례 중 하나를 말하지 못하면,

  근거: R2, R3, FR4
  충족기준: 빈 칸이 채워진 것처럼 보이는 문장이 카드에 없다.

FR6 (Event-driven): When 카드가 완성되면,
                    the 시스템은 shall 사용자에게 소리 내어 말하며 시간을 재도록 안내한다.
  근거: 2단계 가정 2 (시간 기준 검증에 필요) — **확인 필요**
  충족기준: 완성 직후 시간 측정 안내가 카드와 함께 나온다.

FR7 (Unwanted):     If 완성된 카드가 <기준: 3번 정량화에서 확정>을 넘으면,
                    then the 시스템은 shall 줄일 후보 항목을 사용자에게 제시한다.
  근거: R6
  충족기준: 기준을 넘은 카드에 대해 줄일 항목이 제시된다. (기준값은 3번에서 확정)

FR8 (Ubiquitous):   The 시스템은 shall 카드에 PREP이 "출처 확인 불가, 실무에서 통용되는 후보 구조"임을 표시한다.
  근거: R14, 사용자 결정
  충족기준: 모든 카드에 위 표시 문구가 있다.
```
