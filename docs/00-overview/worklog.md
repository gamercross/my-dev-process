# 작업 로그

각 단계 README는 **결과**(무엇이고 어떻게 쓰는지)만 깔끔하게 유지합니다. **과정**
(무엇을 시도했고, 뭘 발견했고, 왜 이렇게 바뀌었는지)은 전부 여기로 모읍니다. 처음
보는 사람은 이 파일을 안 읽어도 됩니다 — README만 봐도 지금 상태를 이해할 수
있어야 합니다. 이 파일은 "왜 지금 이런 모양인지" 궁금할 때만 찾아보는 곳입니다.

## 2026-09-17

### 저장소 뼈대 구성
설계 문서를 하나의 파일로 시작했다가, 단계별로 다루기 쉽도록 `docs/00-overview` ~

### 2단계(문제 분석) 방법론 심화
처음엔 ISO 29148 5요소 요구사항 분류만 있었는데, 이걸 실행 가능한 파이프라인으로
확장: BABOK(수집) → EARS(명세) → Planguage(정량화) → MoSCoW×Kano(우선순위) →
RTM(추적). 각 단계를 검토하며 발견한 것들:
- FURPS+ 약어가 어디에도 안 풀려있던 것을 확인 후 정의 추가
- RTM 표와 `applied-example.md`가 3단계 완료 이후로 갱신 안 된 채 방치돼있던 것 수정
- `applied-example.md`에 수집(1단계) 항목이 통째로 빠져있던 것 보완
- BABOK 9개 기법 중 6개만 쓰면서 나머지 3개를 왜 뺐는지 설명 없었던 것 보완
- Planguage 필드를 6개로 축약해놓고 그 사실을 안 밝혔던 것 — 원본 필드(Budget/Fail/
  Survival 등)와의 관계를 명시

### 3단계(패턴 분석) 파이프라인 구축과 ADR-0001
"후보 도출 → 트레이드오프 평가 → 결정 기록" 3단계 파이프라인을 CLRS 알고리즘
패러다임 / Mark Richards 아키텍처 스타일 / SEI ATAM / Nygard ADR·MADR로 구성.
이 저장소 자체의 아키텍처 결정을 ADR-0001("파일+Claude Code 스킬 하이브리드")로
내림. 이어서 알고리즘 트랙에 실제 예시가 없다는 걸 발견 — Two Sum을 CLRS 4대
패러다임에 대입해보니 어디에도 안 맞는다는 걸 확인하고, "구현 기법 패턴"(Two
Pointers, Sliding Window 등) 계층을 별도로 추가.

### 4단계(패턴 구현) 스켈레톤 제작
ADR-0001에 따라 `.claude/skills/dev-workflow/SKILL.md`를 실제로 작성. 트랙 자동
인식 로직을 스모크 테스트해서 `algorithm-track`/`project-track` 2개만 정확히
잡히는 것 확인. 이 스켈레톤이 "버릴 코드가 아니라 남겨서 키울 코드"라는 걸
Cockburn의 Walking Skeleton 개념으로 뒷받침(Tracer Bullet/Spike와 구분).

### Two Sum 드라이런 — 명령 1·2 수동 검증
자연어 트리거는 이 세션에서 테스트 불가(Claude Code가 세션 시작 시 스킬 목록을
고정) → 대신 SKILL.md 절차를 손으로 따라가는 드라이런 진행. Two Sum을 실제로
1단계에 저장하고, 패턴 검색(명령 2)이 빈 카탈로그에서 올바르게 폴백하는 것까지
확인. **이 과정에서 실제 결함 발견**: 2단계의 5단계 파이프라인이 이 워크플로우
시스템 자체(프로젝트 트랙)로만 검증됐지, 알고리즘 트랙 단순 문제엔 적용해본 적이
없었음 → 2단계 README에 "적용 범위"(경량화 규칙) 절 추가, `checklist.md`에 회고
항목 추가.

### 5~7단계 방법론 보강
1~4단계는 출처 있는 방법론이 갖춰졌는데 5~7단계는 bullet point뿐이었음 → 5단계에
TDD Red-Green-Refactor(Kent Beck) + 동등분할·경계값 분석(ISO/IEC/IEEE 29119),
6단계에 Twelve-Factor App(Heroku), 7단계에 Blameless Postmortem(Allspaw/Etsy →
Google SRE)을 기존 5 Whys 옆에 추가.

### 핵심 피드백 루프 실증
전체 점검에서 가장 중요한 빈틈으로 꼽힌 것: "회고→카탈로그에 적는 것"은 검증됐지만
"카탈로그에서 찾아서 재사용하는 것"은 한 번도 증명 안 됨. Two Sum 회고로
`catalog/patterns.md`에 "해시맵 원패스 탐색" 패턴을 실제로 등록하고, 완전히 별개인
두 번째 문제 Contains Duplicate(LeetCode #217)를 저장한 뒤 "해시" 키워드로
검색해서 **1번에서 등록한 패턴을 실제로 찾아내는 것까지 확인**. 이 김에 카탈로그
카드 형식에 `트랙`/`계층` 필드가 없어서 항목이 쌓이면 알고리즘 기법과 아키텍처
패턴이 뒤섞일 위험도 같이 발견해서 고침.

### 개별 문제용 게이트 로그 신설
`docs/00-overview/gates.md`의 게이트 통과 기록이 이 워크플로우 시스템 자체(메타
프로젝트)의 것만 있고, Two Sum 같은 개별 문제가 어느 게이트까지 통과했는지 남길
곳이 없었음 → 세션 파일에 붙이는 재사용 가능한 "게이트 로그" 블록을 만들고
Two Sum·Contains Duplicate에 실제로 소급 적용. Cooper의 Go/Kill/Hold/Recycle
4개 결정에 **Skip**(2단계 경량화 규칙 때문에 필요)을 추가.

### 규모 등급(Scope Tiers) 신설
"이 7단계를 애초에 다 밟을 가치가 있는 일인가"를 판단하는 기준이 없었음. Cooper
본인이 만든 Stage-Gate Full/Xpress/Lite 등급 구분(그가 겪은 문제와 똑같은
이유 — 작은 프로젝트들이 무거운 프로세스를 그냥 우회해버림)과, GTD의 Two-Minute
Rule(David Allen)을 결합해 `scope-tiers.md`를 만듦. 돌아보니 2단계 경량화 규칙이
사실 Xpress 등급과 같은 개념이었다는 걸 확인.

### 다이어그램 선택 가이드
패턴을 구현하기 전에 뭘 그려야 할지 기준이 없었음 → "어떤 질문에 답하고 싶은가"를
기준으로 순서도(ISO 5807)/C4 모델(Simon Brown)/UML 구조·행동 다이어그램을 고르는
`04-pattern-implementation/03-diagramming-guide.md` 작성. 기존에 그린 다이어그램을
이 기준으로 분류해보니 전부 "행동" 계열이고 "구조" 계열(클래스/컴포넌트/C4
Container)은 하나도 없었다는 것도 확인.

### 루트 README / 전체 다이어그램 동기화
여러 커밋을 거치며 루트 `README.md`와 `00-overview`의 전체 방향 다이어그램이 실제
상태를 못 따라간 게 드러남 — `scope-tiers.md` 링크 누락, 폴더 구조 블록에
`.claude/skills/`·`sessions/`·`adr/` 등이 빠져있었고, 전체 방향 다이어그램은 여전히
1→2→...→7 완전 선형이라 등급별 스킵 경로를 반영 못 하고 있었음. 둘 다 실제 상태에
맞게 다시 씀 — 이 시스템도 자동 동기화 없이는 스스로 낡는다는 걸 보여준 사례.

### PRD 확장 판단을 등급에 연결
`gates.md`의 1단계 완료기준(DoD)이 PRD 확장판을 선택한 경우를 반영 안 하고
있었음 → PRD는 Full 등급 + 프로젝트 트랙에서만 쓴다는 규칙을 `scope-tiers.md`와
연결하고, `gates.md`·`SKILL.md`·1단계 README에 이 분기를 반영.

## 2026-09-19

### 5단계 시작 — Two Sum을 실제로 구현
저장소 최상위에 `implementations/<트랙파일명>/<세션 슬러그>/` 규칙을 새로 만들고
(`docs/`는 방법론용, 실제 코드는 여기), Two Sum을 TDD로 실제 구현: 테스트를 먼저
쓰고 `solution.py`가 없어 실패하는 것 확인(Red) → 브루트포스로 통과(Green) →
`catalog/patterns.md`의 "해시맵 원패스 탐색" 패턴으로 최적화(Refactor), 5개 테스트
유지. Xpress 등급이라 2단계 EARS 명세가 없어서, 대신 경계값 분석(배열 길이 하한,
양끝 인덱스, 음수)과 브루트포스 대비 차등 테스트로 엣지 케이스를 커버함 — 5단계
README의 "Xpress/Lite 등급" 절로 이 대체 규칙을 명문화.

### Contains Duplicate도 같은 방식으로 진행
Two Sum과 완전히 같은 순서(Red→Green→Refactor, 경계값+차등 테스트)로
`implementations/algorithm-track/contains-duplicate/`를 구현. 최적화는 해시맵이
아니라 해시셋 변형이지만 근본 아이디어(한 번 순회하며 지금까지 본 값을 저장)는
동일. 이걸로 `catalog/patterns.md`의 "해시맵 원패스 탐색" 패턴이 Two Sum 전용이
아니라 실제로 여러 문제에 재사용 가능한 일반 패턴이라는 게 두 번째로 확인됨
(첫 확인은 패턴 검색 단계, 이번엔 실제 구현 단계에서).

### 파이프라인 규정 점검 — 5·6단계 DoD가 Full 등급 전제였음
"지금 밟고 있는 파이프라인이 맞는지" 점검하다가, `gates.md`의 5단계 DoD("2단계
EARS 요구사항 전부 커버")와 6단계 DoD("2단계 Planguage Goal 실측")가 여전히 Full
등급을 전제로 쓰여 있는 걸 발견 — PRD/DoD(4번 발견)와 같은 종류의 결함. 이미
`05-implementation/README.md`와 `06-service/README.md`에는 Xpress/알고리즘 트랙용
대체 기준(경계값 분석+차등 테스트, 제출/채점+성능 확인)이 적혀 있었는데
`gates.md`만 안 따라간 상태였음. 두 DoD 행에 등급/트랙별 분기를 추가해서 맞춤.

### 6단계 진행 — 실제 LeetCode 제출 대신 성능 실측
알고리즘 트랙 6단계 DoD("제출/채점+성능 확인")의 "제출"은 이 세션에서 할 수 없음
(LeetCode 계정/브라우저 접근 필요) — 정직하게 한계로 남기고, "채점"은 5단계
테스트로, "성능"은 각 구현 폴더에 새로 만든 `benchmark.py`로 대체. 제약조건
상한에서 측정: Two Sum은 정답을 배열 맨 끝에 둔 최악 케이스로 브루트포스
1842.6ms vs 해시맵 1.147ms(약 1600배). Contains Duplicate는 O(n²)라 상한(10^5)
에서 브루트포스를 직접 못 돌려서, 작은 n(1000/2000/4000)에서 4배씩 증가하는
추세만 확인하고 최적화 버전만 상한에서 측정(5.94ms).

### 7단계 — Two Sum·Contains Duplicate 회고, 두 문제 모두 1→7 완주
두 문제 모두 회고를 작성하며 5 Whys로 두 가지 근본원인을 찾음: (1) 벤치마크의
"최악 케이스"를 실행 결과로 검증하지 않고 사고만으로 확신했던 것 (Two Sum에서
발견), (2) 규정 문서를 한 항목만 고치고 같은 유형의 결함이 다른 곳에도 있는지
전체를 안 훑었던 것 (5·6단계 DoD 건). 둘 다 `catalog/checklist.md`에 새 항목으로
등록. 이걸로 Xpress 등급 알고리즘 문제 두 건이 1단계부터 7단계까지 완전히
한 바퀴 돈 첫 사례가 됨 — 다음은 세 번째 알고리즘 문제로 루프를 더 검증하거나,
Full 등급 프로젝트 트랙으로 처음부터 끝까지 돌려보는 것.

### 첫 Full 등급 프로젝트 트랙 완주 — 카탈로그 검색 CLI
지금까지 Full 등급 규칙(PRD, 2단계 5단계 파이프라인, ADR, Walking Skeleton,
Planguage Goal 실측)은 이 워크플로우 시스템 자체를 만들 때만 쓰였고, 실제로
"새 항목"에 처음부터 끝까지 적용해본 적이 없었다. 카탈로그 검색 CLI(원래
FR2 "패턴 검색"이 지금까지 Claude가 grep하는 방식으로만 존재하던 걸 실제
코드로 채움)를 골라 1→7 전체를 돌림:

- 1단계: PRD 경량형까지 채워서 gates.md의 PRD/DoD 분기를 처음 실사용
- 2단계: EARS 4개, Planguage 2개, MoSCoW×Kano, RTM은 4개(5개 미만)라 생략
  규칙대로 스킵
- 3단계: 후보가 사실상 1개(Layered)라 ATAM 생략, [ADR-0002](../03-pattern-analysis/adr/0002-catalog-search-cli-architecture.md)를
  Nygard 대신 **MADR 최소 템플릿**으로 처음 실사용
- 4~5단계: Walking Skeleton → TDD로 FR1~FR4 구현. 이 과정에서 **테스트
  자체의 버그**(FR3 충족기준을 "출력이 완전히 같아야 한다"로 잘못 해석)를
  발견, `implementations/run_all_tests.py`가 `test_solution.py`만 찾던 것도
  `test_*.py`로 일반화
- 6단계: Twelve-Factor 적용, **이 저장소 최초로 실제 Planguage Goal 측정**
  (Usability 34ms/500ms 목표, Supportability 0개 외부 패키지)
- 7단계: 회고 2건(Two Sum·Contains Duplicate) + 1건(이 프로젝트) 합쳐
  `checklist.md`에 총 4개 항목, `patterns.md`에 첫 프로젝트 트랙 패턴
  ("환경변수 기반 Config 오버라이드") 등록

Xpress 알고리즘 2건 + Full 프로젝트 1건, 총 세 항목이 1→7을 완주함.

### 체크리스트 감사 + 세 번째 알고리즘 문제(Valid Parentheses) 4단계까지
방금 회고에서 나온 checklist.md 항목 4개를 기존 세 항목과 이 시스템 자체의
요구사항에 실제로 적용해봄 — 대부분은 이미 그 자리에서 고쳐져 있었지만, 메타
프로젝트 RTM의 FR2 충족기준("즉시 결과 표시")이 정확히 같은 종류의 모호한
표현으로 남아있던 걸 발견해서 카탈로그 검색 CLI의 실측값(34ms)에 연결해
구체화함. FR1~FR3 구현 위치도 처음으로 채움(그동안 "(미정)"이었음).

이어서 Valid Parentheses(LeetCode #20)를 1단계부터 시작 — 카탈로그에 "스택"·
"괄호" 키워드로 검색했더니 **처음으로 실제 미스**가 나서 표준 카탈로그 폴백
경로를 실증함(지금까지는 항상 Two Sum 패턴이 걸렸음). 4단계까지 브루트포스
(반복 치환)로 정답을 확인하고, 5단계(스택 최적화)는 다음으로 남김.

### Valid Parentheses 5단계 — 처음으로 "Red 없는" TDD 사이클
4단계 브루트포스가 이미 정답 자체는 맞았기 때문에(느릴 뿐), Two Sum 때와 달리
Red 구간이 없었다 — 동등분할/경계값 분석(길이 하한, 홀수 길이 클래스, 패리티로
못 거르는 짝수 길이 구조 오류, 길이 상한)으로 테스트 7개를 먼저 설계해 브루트
포스에 통과시킨 뒤, Refactor 자리에서 스택 기반 O(n)으로 교체(빠른 실패로
"홀수 길이는 항상 무효" 조건도 코드에 반영). `run_all_tests.py`로 4개 구현
24개 테스트 전체 통과 확인.

### Valid Parentheses 6단계 — 지난 교훈을 실제로 적용
Two Sum 벤치마크 실수(주장한 "최악 케이스"가 실제로는 아니었던 것)를
`catalog/checklist.md`에 체크리스트로 남긴 게 이번에 실제로 도움이 됨 —
상한(n=10,000)에서 바로 측정하지 않고, 완전 중첩 문자열을 여러 크기
(1000/2000/4000/8000)에서 먼저 돌려 약 4배씩 늘어나는 진짜 O(n²) 추세를
확인한 뒤에 상한을 측정: 브루트포스 179.2ms → 스택 0.383ms(약 468배).
체크리스트가 실제로 재발을 막은 첫 사례.

### Valid Parentheses 7단계 — 회고에 처음으로 "새로 발견한 어려움 없음"
지난 두 회고의 체크리스트 항목이 이번 항목 전체를 예방하는 걸 실제로 확인했다
(3단계 폴백 경로, 6단계 벤치마크 검증). 억지로 5 Whys를 만들지 않고 정직하게
"이번엔 새 문제 없음"으로 회고를 마침 — 이것도 이 시스템이 원래 하려던 일
(배운 걸 재사용해서 같은 실수를 안 하는 것)이 실제로 작동하고 있다는 증거다.
`catalog/patterns.md`에 두 번째 구현 기법 패턴("스택 기반 매칭") 등록. 이걸로
Xpress 알고리즘 3건 + Full 프로젝트 1건, 총 4개 항목이 1→7을 완주함.

### 트래커 신설 + 네 번째 알고리즘 문제(Contains Duplicate II) 1→7 완주
항목이 늘어나면서 "지금까지 뭘 풀었고 어디까지 왔는지"를 한눈에 보기 어려워짐
→ `docs/01-problem-save/sessions/README.md`에 트래커 표(문제/트랙/등급/패턴/
게이트/테스트 개수) 신설, 루트 README에서 바로 연결.

이어서 Contains Duplicate II(LeetCode #219, 거리 제한 k가 붙은 변형)를 1→7
전체 진행. 3단계에서 "해시맵" 검색이 기존 패턴을 정확히 찾아냈고(세 번째
재사용), 이번엔 "봤는지 여부"가 아니라 "마지막으로 본 인덱스"를 저장하는
변형이었는데도 패턴의 핵심 설명이 그대로 들어맞아서 `catalog/patterns.md`의
해당 패턴 설명 자체를 이 변형을 포함하도록 일반화했다. 5·6단계 모두 지난
회고의 체크리스트(벤치마크 추세 검증 등)가 다시 예방 역할을 했고, 7단계
회고에서도 새로 발견한 어려움은 없었다.

이걸로 Xpress 알고리즘 4건 + Full 프로젝트 1건, 총 5개 항목이 1→7 완주
(`run_all_tests.py` 기준 31개 테스트 전체 통과). 항목이 늘면서 06/07단계
README의 개별 링크 나열이 무한정 길어질 위험이 있어, 두 곳 다 트래커 표로
가리키는 방식으로 바꿈.

시나리오가 둘을 실제로 갈랐다. FR5(REPORT_OUTPUT 환경변수)는 첫 프로젝트의

5단계에서 진짜 흥미로운 지점: 이 도구는 저장소 자신의 테스트 스위트를
집계하는데, 그 집계 로직을 검증하는 테스트 자신도 그 스위트의 일부라서
기본 동작 그대로 테스트하면 무한 재귀가 될 수 있었다. 실제로 재귀를
터뜨리기 전에 의존성 주입(가짜 loader)으로 설계 시점에 미리 끊었고, 이후
(1) 이 프로젝트 테스트만 단독 실행 (2) 전체 스위트로 실행 두 가지를 실제로
돌려서 재귀 없이 끝난다는 걸 실행으로 재확인했다. "자기 자신을 실행하는
