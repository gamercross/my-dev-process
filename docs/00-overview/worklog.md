(무엇을 시도했고, 뭘 발견했고, 왜 이렇게 바뀌었는지)은 전부 여기로 모읍니다. 처음
보는 사람은 이 파일을 안 읽어도 됩니다 — README만 봐도 지금 상태를 이해할 수
있어야 합니다. 이 파일은 "왜 지금 이런 모양인지" 궁금할 때만 찾아보는 곳입니다.

### 2단계(문제 분석) 방법론 심화
처음엔 ISO 29148 5요소 요구사항 분류만 있었는데, 이걸 실행 가능한 파이프라인으로
확장: BABOK(수집) → EARS(명세) → Planguage(정량화) → MoSCoW×Kano(우선순위) →
RTM(추적). 각 단계를 검토하며 발견한 것들:
- FURPS+ 약어가 어디에도 안 풀려있던 것을 확인 후 정의 추가
- RTM 표와 `applied-example.md`가 3단계 완료 이후로 갱신 안 된 채 방치돼있던 것 수정
- `applied-example.md`에 수집(1단계) 항목이 통째로 빠져있던 것 보완
- BABOK 9개 기법 중 6개만 쓰면서 나머지 3개를 왜 뺐는지 설명 없었던 것 보완
- Planguage 필드를 6개로 축약해놓고 그 사실을 안 밝혔던 것 — 원본 필드(Budget/Fail/
  Survival 등)와의 관계를 명시

### 3단계(패턴 분석) 파이프라인 구축과 ADR-0001
"후보 도출 → 트레이드오프 평가 → 결정 기록" 3단계 파이프라인을 CLRS 알고리즘
패러다임 / Mark Richards 아키텍처 스타일 / SEI ATAM / Nygard ADR·MADR로 구성.
이 저장소 자체의 아키텍처 결정을 ADR-0001("파일+Claude Code 스킬 하이브리드")로
내림. 이어서 알고리즘 트랙에 실제 예시가 없다는 걸 발견 — Two Sum을 CLRS 4대
패러다임에 대입해보니 어디에도 안 맞는다는 걸 확인하고, "구현 기법 패턴"(Two
Pointers, Sliding Window 등) 계층을 별도로 추가.

### 4단계(패턴 구현) 스켈레톤 제작
ADR-0001에 따라 `.claude/skills/dev-workflow/SKILL.md`를 실제로 작성. 트랙 자동
인식 로직을 스모크 테스트해서 `algorithm-track`/`project-track` 2개만 정확히
잡히는 것 확인. 이 스켈레톤이 "버릴 코드가 아니라 남겨서 키울 코드"라는 걸
Cockburn의 Walking Skeleton 개념으로 뒷받침(Tracer Bullet/Spike와 구분).

### Two Sum 드라이런 — 명령 1·2 수동 검증
자연어 트리거는 이 세션에서 테스트 불가(Claude Code가 세션 시작 시 스킬 목록을
고정) → 대신 SKILL.md 절차를 손으로 따라가는 드라이런 진행. Two Sum을 실제로
1단계에 저장하고, 패턴 검색(명령 2)이 빈 카탈로그에서 올바르게 폴백하는 것까지
확인. **이 과정에서 실제 결함 발견**: 2단계의 5단계 파이프라인이 이 워크플로우
시스템 자체(프로젝트 트랙)로만 검증됐지, 알고리즘 트랙 단순 문제엔 적용해본 적이
없었음 → 2단계 README에 "적용 범위"(경량화 규칙) 절 추가, `checklist.md`에 회고
항목 추가.

### 5~7단계 방법론 보강
1~4단계는 출처 있는 방법론이 갖춰졌는데 5~7단계는 bullet point뿐이었음 → 5단계에
TDD Red-Green-Refactor(Kent Beck) + 동등분할·경계값 분석(ISO/IEC/IEEE 29119),
6단계에 Twelve-Factor App(Heroku), 7단계에 Blameless Postmortem(Allspaw/Etsy →
Google SRE)을 기존 5 Whys 옆에 추가.

### 핵심 피드백 루프 실증
전체 점검에서 가장 중요한 빈틈으로 꼽힌 것: "회고→카탈로그에 적는 것"은 검증됐지만
"카탈로그에서 찾아서 재사용하는 것"은 한 번도 증명 안 됨. Two Sum 회고로
`catalog/patterns.md`에 "해시맵 원패스 탐색" 패턴을 실제로 등록하고, 완전히 별개인
두 번째 문제 Contains Duplicate(LeetCode #217)를 저장한 뒤 "해시" 키워드로
검색해서 **1번에서 등록한 패턴을 실제로 찾아내는 것까지 확인**. 이 김에 카탈로그
카드 형식에 `트랙`/`계층` 필드가 없어서 항목이 쌓이면 알고리즘 기법과 아키텍처
패턴이 뒤섞일 위험도 같이 발견해서 고침.

### 개별 문제용 게이트 로그 신설
`docs/00-overview/gates.md`의 게이트 통과 기록이 이 워크플로우 시스템 자체(메타
프로젝트)의 것만 있고, Two Sum 같은 개별 문제가 어느 게이트까지 통과했는지 남길
곳이 없었음 → 세션 파일에 붙이는 재사용 가능한 "게이트 로그" 블록을 만들고
Two Sum·Contains Duplicate에 실제로 소급 적용. Cooper의 Go/Kill/Hold/Recycle
4개 결정에 **Skip**(2단계 경량화 규칙 때문에 필요)을 추가.

### 규모 등급(Scope Tiers) 신설
"이 7단계를 애초에 다 밟을 가치가 있는 일인가"를 판단하는 기준이 없었음. Cooper
본인이 만든 Stage-Gate Full/Xpress/Lite 등급 구분(그가 겪은 문제와 똑같은
이유 — 작은 프로젝트들이 무거운 프로세스를 그냥 우회해버림)과, GTD의 Two-Minute
Rule(David Allen)을 결합해 `scope-tiers.md`를 만듦. 돌아보니 2단계 경량화 규칙이
사실 Xpress 등급과 같은 개념이었다는 걸 확인.

여러 커밋을 거치며 루트 `README.md`와 `00-overview`의 전체 방향 다이어그램이 실제

## 2026-09-19

### 5단계 시작 — Two Sum을 실제로 구현
저장소 최상위에 `implementations/<트랙파일명>/<세션 슬러그>/` 규칙을 새로 만들고
(`docs/`는 방법론용, 실제 코드는 여기), Two Sum을 TDD로 실제 구현: 테스트를 먼저
쓰고 `solution.py`가 없어 실패하는 것 확인(Red) → 브루트포스로 통과(Green) →
`catalog/patterns.md`의 "해시맵 원패스 탐색" 패턴으로 최적화(Refactor), 5개 테스트
유지. Xpress 등급이라 2단계 EARS 명세가 없어서, 대신 경계값 분석(배열 길이 하한,
양끝 인덱스, 음수)과 브루트포스 대비 차등 테스트로 엣지 케이스를 커버함 — 5단계
README의 "Xpress/Lite 등급" 절로 이 대체 규칙을 명문화.

### Contains Duplicate도 같은 방식으로 진행
Two Sum과 완전히 같은 순서(Red→Green→Refactor, 경계값+차등 테스트)로
`implementations/algorithm-track/contains-duplicate/`를 구현. 최적화는 해시맵이
아니라 해시셋 변형이지만 근본 아이디어(한 번 순회하며 지금까지 본 값을 저장)는
동일. 이걸로 `catalog/patterns.md`의 "해시맵 원패스 탐색" 패턴이 Two Sum 전용이
아니라 실제로 여러 문제에 재사용 가능한 일반 패턴이라는 게 두 번째로 확인됨
(첫 확인은 패턴 검색 단계, 이번엔 실제 구현 단계에서).

### 파이프라인 규정 점검 — 5·6단계 DoD가 Full 등급 전제였음
"지금 밟고 있는 파이프라인이 맞는지" 점검하다가, `gates.md`의 5단계 DoD("2단계
EARS 요구사항 전부 커버")와 6단계 DoD("2단계 Planguage Goal 실측")가 여전히 Full
등급을 전제로 쓰여 있는 걸 발견 — PRD/DoD(4번 발견)와 같은 종류의 결함. 이미
`05-implementation/README.md`와 `06-service/README.md`에는 Xpress/알고리즘 트랙용
대체 기준(경계값 분석+차등 테스트, 제출/채점+성능 확인)이 적혀 있었는데
`gates.md`만 안 따라간 상태였음. 두 DoD 행에 등급/트랙별 분기를 추가해서 맞춤.

### 6단계 진행 — 실제 LeetCode 제출 대신 성능 실측
알고리즘 트랙 6단계 DoD("제출/채점+성능 확인")의 "제출"은 이 세션에서 할 수 없음
(LeetCode 계정/브라우저 접근 필요) — 정직하게 한계로 남기고, "채점"은 5단계
테스트로, "성능"은 각 구현 폴더에 새로 만든 `benchmark.py`로 대체. 제약조건
상한에서 측정: Two Sum은 정답을 배열 맨 끝에 둔 최악 케이스로 브루트포스
1842.6ms vs 해시맵 1.147ms(약 1600배). Contains Duplicate는 O(n²)라 상한(10^5)
에서 브루트포스를 직접 못 돌려서, 작은 n(1000/2000/4000)에서 4배씩 증가하는
추세만 확인하고 최적화 버전만 상한에서 측정(5.94ms).
